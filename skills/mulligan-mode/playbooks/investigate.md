# Investigate

A question, not a change: how does it work, why is it like this, are we sure, should we pick A or B. Nothing is edited.

1. Decide which question it is. Behaviour → the **how** skill. Motivation or history → the **reading-the-flight** skill. Both → run both and combine.
2. Answer from evidence. Cite `file:line`, commits, PRs, docs. Where the evidence runs out, say so and label what you infer.
3. If the developer is choosing between options, give a recommendation with a trade-off table, and say what would change your mind.
4. If the answer shows that code should change, stop and say so. The change is a new task (Bug fix or Feature), started when the developer agrees.

**Reply:** the answer first, then the evidence, then open questions. For "are we sure?", give your honest judgement — if the question rests on a false assumption, say so.
